# 后台普通用户登录与空间成员视图设计

**日期**：2026-04-05
**状态**：设计稿
**范围**：`apps/server` / `apps/web`

## 目标

让已登录但不是 `platform_admin` / `space_admin` 的普通用户也能进入后台页，并根据其实际成员身份展示不同能力：

1. 仅普通登录用户：能看到个人信息页和分享中心的“我的分享”，且只能操作自己创建的分享。
2. 普通登录用户且是某空间成员：能看到空间管理入口，但右侧只保留“编辑文档”。
3. `space_admin` / `platform_admin`：保持现有完整后台能力不变。

## 非目标

1. 不新增新的数据库角色。
2. 不改变现有 `platform_admin` / `space_admin` 的权限语义。
3. 不把后台普通用户改成可访问所有管理操作。
4. 不改文档正文编辑器本身的权限模型。

## 核心思路

采用“**角色 + 能力视图**”的组合模型。

- 角色继续由后端现有 `platform_admin` / `space_admin` 体系决定。
- 能力视图用于决定后台壳页显示什么菜单、空间管理页右侧显示什么操作。
- 后端继续做最终拦截，前端只负责可见性优化。

这样可以避免把“能看见”误认为“能操作”，也能让普通登录用户进入后台时不看到空白或报错页。

## 视图划分

### 1. 个人信息视图

适用对象：

- 所有已登录用户

展示内容：

- 个人资料
- 头像
- 修改密码
- 与当前账号相关的基础信息

### 2. 自助分享视图

适用对象：

- 所有已登录用户

展示内容：

- “我的分享”列表
- 自己创建的分享可执行改码、延期、设永久、取消分享
- 其他人的分享仅可见，不可操作

### 3. 空间成员视图

适用对象：

- 已登录普通用户
- 且该用户是至少一个空间的成员

展示内容：

- 空间管理页
- 空间列表中的当前成员空间
- 空间管理右侧仅显示“编辑文档”

### 4. 空间管理视图

适用对象：

- `space_admin`
- `platform_admin`

展示内容：

- 现有空间管理全部能力
- 成员管理
- 状态/删除/转让
- 设置类操作
- 其他已有管理动作

## 菜单调整

### 左侧后台菜单

1. 普通登录用户同时显示“个人信息”与“分享中心/我的分享”。
2. 空间成员用户显示“个人信息”“分享中心/我的分享”与“空间管理”。
3. `space_admin` / `platform_admin` 显示现有完整菜单。

### 空间管理页右侧操作区

1. 普通成员模式只显示“编辑文档”。
2. `space_admin` / `platform_admin` 继续显示完整操作区。
3. 普通用户在“我的分享”里仅对自己创建的分享显示行内操作。
4. 其余按钮统一隐藏，不做“禁用态露出”。

### “编辑文档”菜单归位

1. 将“编辑文档”折叠到“设置”子菜单下。
2. 右侧操作区仍保留快捷入口，但和菜单结构一致。
3. 菜单与右侧操作区都共享同一套能力判断，避免入口分裂。

## 后端约束

1. `/admin/profile` 对所有已登录用户开放。
2. `/admin/document-shares` 对所有已登录用户开放，但普通用户只允许 `view=mine`，且只允许改码、延期、设永久、取消自己创建的分享。
3. 非管理员用户访问 `/admin/users`、`/admin/spaces` 等管理接口时，后端仍应返回 403 或业务拒绝。
4. 管理能力判断继续以现有角色和空间范围为准，不新增“普通管理员”角色。
5. 如果前端需要判断是否展示空间成员视图，应由后台返回一个轻量能力摘要，或由现有用户/空间成员数据推导。

## 前端约束

1. 后台壳页菜单必须和真实权限一致。
2. 空间成员只能看到“编辑文档”这一类低风险入口。
3. 普通用户在分享中心只能看到“我的分享”，但自己创建的分享行可以继续编辑。
4. 不允许仅靠前端隐藏来表达权限，后端仍必须兜底。
5. 所有菜单/按钮显示逻辑应收敛到统一的能力判断函数，避免在多个页面重复写条件。

## 数据与权限来源

建议优先复用现有信息：

- 当前登录用户的后台角色：`platform_admin` / `space_admin`
- 用户在空间中的成员身份
- 用户可管理的空间 scope

如果前端现有数据不足以稳定判断成员态，再补一个轻量后台接口用于返回“后台能力摘要”。

## 测试清单

1. 普通登录用户进入后台只看到个人信息页。
2. 普通登录用户可看到“分享中心/我的分享”，且只对自己创建的分享显示行内操作。
3. 普通登录用户如果是空间成员，可看到空间管理，但右侧只剩“编辑文档”。
4. `space_admin` / `platform_admin` 的既有空间管理按钮不回退。
5. “编辑文档”从独立入口折叠到“设置”子菜单后，菜单结构测试通过。
6. 直接访问受限后台路由仍被后端拒绝。

## 风险与兼容性

1. 风险点在于菜单可见性与后端授权不一致，因此必须双层校验。
2. 如果普通用户能进入后台壳页但没有空间，也要保证页面不是空白，而是个人信息页。
3. 如果空间成员态判断依赖额外接口，要避免增加后台首屏明显抖动。

## 实施建议

1. 先补后台能力摘要或现有数据组合判断。
2. 再改后台壳页菜单可见性。
3. 再改空间管理页右侧按钮与“设置”子菜单。
4. 最后补前后端回归测试。
